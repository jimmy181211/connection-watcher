## 1. 先建立整体认识

SocketSight 做的事情可以压缩成六步：

1. 读取用户启用的监视规则。
2. 按设定的间隔读取 Windows TCP 连接表。
3. 判断哪些连接符合规则。
4. 跟踪匹配连接是新出现、仍然存在还是已经结束。
5. 为新连接收集 Windows 能提供的进程和应用背景信息。
6. 写入 CSV，并按照规则选择静默记录、托盘提示或弹窗警报。

先记住这条主线。以后看到一个类或方法时，先问：“它属于这六步中的哪一步？”这样比从最大的窗体文件第一行开始阅读更容易。

## 2. 代码地图：每一层负责什么

```text
用户界面和按钮
ConnectionWatcher.App
        │
        ▼
规则、监控、连接状态、进程背景、日志
ConnectionWatcher.Core
        │
        ▼
Windows TCP 表、进程、服务和文件系统
```

### `ConnectionWatcher.Core`

这是业务核心，不应该依赖某个具体窗口。

- `Models`：规则、连接、事件和进程背景的数据结构。
- `Rules`：验证规则并判断连接是否匹配。
- `Monitoring`：读取连接、跟踪连接、收集进程信息和运行监控循环。
- `Logging`：写入 CSV，读取旧版本日志并处理特殊字符。
- `Configuration`：保存和读取用户设置。

### `ConnectionWatcher.App`

这是用户看见和操作的部分。

- `UI`：主页、规则编辑、事件详情、帮助中心和警报窗口。
- `Localization`：七种界面语言和启动提示语。
- `Services`：托盘、提示音、Windows 登录启动、更新检查和安装语言处理。
- `Assets`：图标和其他界面资源。

### 其他目录

- `tests`：核心功能、旧日志兼容性、多语言和 DPI 布局测试。
- `docs`：给用户看的项目说明和使用说明。
- `learning`：开发者学习材料。
- `packaging`：Inno Setup 安装包定义。
- `scripts`：自动构建、测试、打包和生成校验文件。

### 3.2 基础掌握

基础掌握是在快速入门的基础上真正动手。下面五个主题都属于这一层：观看对应课程后，还要阅读核心源码、完成小练习并通过自测。

各主题的“建议掌握时间”已经包含相关课程、练习、源码阅读和自测，不需要在12–18小时之外再次累加。部分活动会同时帮助理解多个主题，因此各小节时间也不必机械相加。

#### 3.2.1 C# 基础

你需要理解类、接口、属性、集合、枚举、异常、可空类型和记录类型。

这些概念决定了程序如何表示一条规则、一条连接和一个事件。例如，`MonitoringRule`不是一个页面控件，而是一个独立的数据对象；规则匹配函数接收连接和规则，返回匹配结果。

**建议掌握时间：**2–3小时，包含相关课程、源码阅读、练习和自测。

**推荐方法：**先完成上面的 Pluralsight C# 短课，再打开 `Models` 目录，对每个类型回答“它保存什么数据”。

**自测：**你能不看代码解释类、接口和枚举的区别，并能自己写一个包含 IP、端口和启用状态的规则类。

#### 3.2.2 异步编程和取消

`async/await`让程序等待时不冻结窗口。`Task`表示一个可能稍后完成的工作，`CancellationToken`让监控循环能够在用户点击“停止监控”或关闭程序时安全退出。

本项目的监控循环不能在界面线程中直接运行无限循环，否则按钮和窗口会失去响应。动态修改检查间隔时，等待中的循环还需要被及时唤醒并使用新设置。

**建议掌握时间：**2–4小时，包含相关课程、源码阅读、练习和自测。

**推荐方法：**先写一个每秒输出一次文字、可用取消令牌停止的控制台程序，再阅读 `MonitoringEngine`。

**自测：**你能解释为什么 `Thread.Sleep`不适合直接放在界面线程中，也能说明取消令牌和普通布尔变量的区别。

#### 3.2.3 WinForms 和布局

WinForms 是 Windows 桌面界面框架。你需要理解窗体、控件、事件、布局容器、锚定、自动调整大小和 UI 线程。

SocketSight 的很多修改不是业务逻辑，而是布局问题：按钮文字被截断、表头需要居中、不同语言文字长度不同。因此不要只调整某一个控件的坐标，还要考虑窗口缩放、字体和最长翻译。

**建议掌握时间：**3–5小时，包含相关课程、源码阅读、练习和自测。

**推荐方法：**先做一个包含按钮、表格和设置区域的小窗体，然后阅读 `MainForm`、规则窗口和事件详情窗口。

**自测：**把系统显示比例改为 125% 或 150%，切换到较长的语言，检查所有文字、按钮和表格是否仍然可见。

#### 3.2.4 网络基础：IP、端口和 TCP

IP 地址标识网络主机，端口标识主机上的服务或应用入口。一个 TCP 连接通常可以表示为：

```text
本地 IP:本地端口  →  远程 IP:远程端口
```

SocketSight 观察的是 Windows 报告的 TCP 连接表，而不是读取数据包正文。因此它能知道端点、状态和进程 ID，但不能知道通信内容，也不能可靠判断哪一方最初发起了连接。

**建议掌握时间：**2–3小时，包含相关课程、源码阅读、练习和自测。

**推荐方法：**用 `netstat -ano` 或资源监视器观察连接，再把一条输出对应到 `TcpConnectionInfo`。

**自测：**你能解释远程端口 1433 和本地临时端口有什么不同，并能说明“连接匹配规则”不等于“发现恶意软件”。

#### 3.2.5 进程、PID、父进程和权限

PID 是 Windows 给进程分配的数字编号。连接表通常只能直接告诉程序“这个连接对应哪个 PID”。SocketSight 再根据 PID 尝试取得进程名称、路径、文件产品信息、父级或宿主进程，以及相关 Windows 服务。

这些内容是调查线索，不是绝对结论。浏览器、代理、VPN 或网页组件可能早已运行，真正产生请求的应用关系可能无法从连接表中完全还原；进程结束或权限不足时，部分字段也可能为空。

**建议掌握时间：**2–3小时，包含相关课程、源码阅读、练习和自测。

**推荐方法：**使用任务管理器、资源监视器和 PowerShell 的 `Get-Process`观察 PID，再阅读 `WindowsProcessContextProvider`。

**自测：**你能解释为什么“拥有连接的 PID”不一定等于“最终幕后应用”，并能说出权限不足时程序应如何处理。

## 4. 逐步读懂核心逻辑

推荐按下面的顺序阅读。每读完一个文件，用自己的话回答三个问题：它接收什么、输出什么、不负责什么。

1. `MonitoringRule.cs`：规则允许用户表达哪些条件。
2. `TcpConnectionInfo.cs`：Windows 连接在程序中如何表示。
3. `RuleMatcher.cs`：远程 IP、远程端口和本地端口如何匹配。
4. `WindowsTcpConnectionProvider.cs`：连接数据从 Windows 哪里来。
5. `ConnectionTracker.cs`：怎样避免同一连接被反复记录。
6. `MonitoringEngine.cs`：读取、匹配、跟踪和提醒怎样串起来。
7. `ProcessContext.cs`和`WindowsProcessContextProvider.cs`：怎样补充应用背景。
8. `ConnectionEvent.cs`和`CsvEventLogger.cs`：事件怎样保存并兼容旧日志。
9. `MainForm.cs`和`EventDetailsForm.cs`：核心结果怎样显示给用户。
10. `Program.cs`、启动画面和测试文件：程序如何启动，哪些行为必须保持正确。

## 5. 连接生命周期：项目最重要的设计

### 5.1 为什么需要去重

程序每次检查都会再次看到仍然存在的连接。如果每次都写一行，一个持续一小时的连接会产生几千条重复记录。

`ConnectionTracker`保存当前观察状态：第一次看到连接时创建事件；继续看到时只更新最后观察时间；真正结束后才固定结束时间。

### 5.2 为什么是两秒宽限期

连接可能因为 Windows 列表刷新或读取时机，在一次检查中暂时消失。程序不会立刻判定它结束，而是等待两秒真实时间。如果连接在两秒内重新出现，仍算同一条记录；超过两秒后再次出现，才创建新记录。

这里必须使用真实时间，而不能简单地说“连续缺失两次”。因为用户可以把检查间隔改为 0.5–10 秒，缺失两次在不同设置下代表完全不同的时间长度。

### 5.3 停止后重新开始会怎样

停止监控后程序没有继续观察连接，无法知道这段时间内连接是否中断。因此重新开始监控时，会建立新的观察记录。这是信息诚实性的取舍：程序不假装知道它没有观察到的时间段。

### 5.4 观察时长的含义

时长从程序第一次发现连接开始计算，不一定等于 Windows 记录的精确建立时间。检查间隔越长，发现时间的不确定范围越大。文档和界面都应把它称为“已观察时长”，而不是绝对的连接时长。

## 6. 规则、日志和界面之间的边界

### 6.1 规则匹配

规则决定“用户想关注什么”。同一条规则内的条件采用“并且”关系；不同的已启用规则采用“或者”关系。如果同一连接符合多条规则，只产生一条事件，并执行提醒强度最高的操作。

规则匹配应放在核心层，而不是按钮事件里。这样可以独立测试，也不会让 UI 代码变成网络分析代码。

### 6.2 清空显示不删除日志

“清空显示”保存一个时间分界点，只改变页面显示范围，不删除 CSV。这样用户可以保持页面整洁，同时保留调查资料。这个设计说明“底层数据”和“当前视图”是两个不同概念。

### 6.3 CSV 向后兼容

新版事件增加了应用背景字段，但用户可能已经有旧版本日志。读取器需要根据表头或列数识别旧格式，为缺失字段提供空值；写入器使用当前格式，并正确处理逗号、换行和引号。

修改日志格式时，至少要测试：新程序读取旧文件、特殊字符、空字段、损坏行和文件大小限制。

## 7. 启动、语言和安装包是怎样连接的

### 7.1 安装语言为什么能影响软件语言

安装程序和主程序是两个独立的进程。安装器把用户选择的语言写入安装目录中的一个小文件；主程序启动时读取它，应用语言设置后删除这个临时文件。

这个流程的关键点是：安装语言是一次性的“交接信息”，不是把安装器语言永久写死在程序里。规则、日志和其他设置仍然保存在用户数据目录，不会因为换语言而丢失。

### 7.2 启动画面为什么只在需要时出现

程序没有人为增加等待时间。它先准备主窗口；如果总启动时间超过约 0.5 秒，辅助线程才显示启动画面。主窗口准备好后，启动画面自动关闭。

这样既能在较慢电脑上给用户反馈，又不会让快速启动的用户每次都看到多余窗口。启动画面中的文字是本地资源，不代表程序正在联网。

### 7.3 为什么最终安装包只有一个

用户只需要下载一个 `SocketSight-Setup-win-x64.exe`。安装器内部包含程序和七种语言资源；安装后程序采用自包含的多文件发布方式，不要求用户另外安装 .NET 运行环境。

开发者看到的 `artifacts`、`dist`和`Final-Share`是不同阶段的构建结果，不是给普通用户重复使用的三个安装包。

## 8. 多语言和界面质量

多语言不是简单地把英文逐字替换成其他语言。不同语言的文字长度、大小写和字体宽度都不同，因此界面需要：

- 统一使用资源字典，不把用户可见文字散落在业务代码中。
- 测试最长的标题、按钮和表格列名。
- 允许控件自动伸展，避免固定宽度造成文字被截断。
- 在事件表中让列标题居中、数据左对齐，兼顾可读性。
- 在不同 DPI 比例下运行 UI smoke 测试。

你可以先修改一个帮助文字，再切换七种语言和 125% DPI，观察修改是否只影响预期位置。这是学习本地化和响应式布局的好练习。

## 9. 测试、调试和安全修改

### 9.1 基础命令

```powershell
dotnet build ConnectionWatcher.sln --configuration Release
dotnet run --project tests\ConnectionWatcher.Tests\ConnectionWatcher.Tests.csproj --configuration Release
```

完整发布时运行：

```powershell
scripts\build-release.ps1
```

脚本会构建、测试、发布自包含程序、生成安装器、整理当前文档并生成 SHA-256 校验文件。

### 9.2 一个功能应该怎样修改

以“增加一个事件字段”为例：

1. 先定义字段含义和空值行为。
2. 在数据来源处收集它，不要让界面负责调查逻辑。
3. 更新事件模型和 CSV 读写。
4. 保证旧 CSV 仍然能打开。
5. 事件详情显示完整信息，主表只保留摘要。
6. 为核心行为增加测试。
7. 检查七种语言和不同 DPI 下的布局。
8. 更新英文基准文档，再翻译其他语言。
9. 在 `RELEASE_NOTES.md` 中说明用户能感知的变化。

### 9.3 用断点追踪一次连接

选择一个明确的测试目标，依次观察：

```text
Windows 连接表
    → 连接提供器
    → 规则匹配器
    → 连接跟踪器
    → 进程背景收集
    → 事件日志
    → 界面和提醒
```

每到一层就记录输入和输出。你不需要一次读懂所有方法，只要能解释这一条数据是怎样向前流动的。

## 10. 之后可以深入什么

当前版本先把 TCP 规则监控、记录和应用线索做好。UDP 并不是简单地再读取一张表；如果要可靠获得远程端点和应用归属，通常需要更底层的 Windows 事件追踪、权限处理和更多测试。

以后可以继续学习：

- Windows 事件追踪和更强的网络归属能力。
- 依赖注入和更清晰的界面与业务分离。
- 配置和日志格式的版本迁移。
- GitHub Actions 自动测试和发布。
- 更完整的集成测试和性能测试。

你不需要把这些内容全部学完才算成功。对这个项目来说，能够解释一个类、验证一个行为、完成一次小而安全的修改，就是很扎实的进步。
