# TCP Connection Watcher 开发者学习教程

这份教程面向已经学过基础编程、但还不熟悉完整桌面软件项目的学生。目标不是让你立刻重写程序，而是帮助你沿着一条清楚的路线读懂现有代码，并逐步具备修改它的能力。

## 1. 先理解软件在做什么

程序的核心循环很简单：

1. 按设定的时间间隔读取Windows TCP连接表。
2. 用用户启用的规则筛选连接。
3. 判断匹配连接是新出现、仍然存在，还是已经结束。
4. 只在新匹配时收集程序背景资料并执行提醒。
5. 把事件写入CSV，再把主要信息显示在界面上。

把这五步记住，后面的大多数代码都能放回正确的位置。

## 2. 阅读代码前需要的知识

不需要先学完所有内容。遇到对应代码时，再补相应知识即可。

- C#基础：类、接口、集合、异常、事件和可空类型。
- 异步编程：`Task`、`async/await`、`CancellationToken`。
- WinForms：窗体、控件、布局、事件处理和系统托盘。
- 网络基础：IP、端口、TCP状态、本地端点和远程端点。
- 操作系统基础：进程、PID、父进程、Windows服务和权限。
- 文件与数据：JSON配置、CSV转义、编码和兼容旧格式。
- 工程工具：Git、GitHub、.NET构建、测试、安装包和SHA-256。

## 3. 项目架构

```text
界面与用户操作
ConnectionWatcher.App
        │
        ▼
规则、监控、连接状态、日志
ConnectionWatcher.Core
        │
        ▼
Windows TCP表、进程与服务信息、文件系统
```

### `ConnectionWatcher.Core`

这里放不依赖具体页面的核心逻辑：

- `Models`：规则、连接、事件和程序背景资料的数据结构。
- `Rules`：检查规则是否合法，并判断连接是否符合规则。
- `Monitoring`：读取连接、追踪连接状态、收集进程资料并运行监控循环。
- `Logging`：把事件写入CSV，并读取新旧版本的CSV记录。
- `Configuration`：保存和读取用户设置。

### `ConnectionWatcher.App`

这里负责用户能看见和操作的部分：

- `UI`：主页、规则编辑、事件详情、帮助中心和警报窗口。
- `Localization`：七种界面语言的文本。
- `Services`：提示音、开机启动和手动更新检查。
- `Assets`：图标和图片。

### `tests`

- `ConnectionWatcher.Tests`：验证规则、追踪、CSV兼容、动态间隔和程序背景资料。
- `ConnectionWatcher.UiSmoke`：打开不同语言与缩放比例的页面，检查控件是否被遮挡或挤出窗口。

## 4. 推荐的读码顺序

不要从最大的窗体文件第一行一路读到底。按一条连接的生命周期阅读更容易：

1. `MonitoringRule.cs`：用户能表达什么监视条件。
2. `TcpConnectionInfo.cs`：Windows连接在程序中的样子。
3. `RuleMatcher.cs`：规则怎样匹配连接。
4. `WindowsTcpConnectionProvider.cs`：连接数据从哪里来。
5. `ConnectionTracker.cs`：怎样避免每次检查都重复记录。
6. `MonitoringEngine.cs`：整个后台循环怎样组织。
7. `ProcessContext.cs`和`WindowsProcessContextProvider.cs`：怎样补充应用背景。
8. `ConnectionEvent.cs`和`CsvEventLogger.cs`：结果怎样保存并兼容旧日志。
9. `MainForm.cs`和`EventDetailsForm.cs`：数据怎样呈现给用户。
10. `Program.cs`测试文件：作者认为哪些行为必须保持正确。

每读完一个文件，用自己的话回答三个问题：它接收什么、它输出什么、它不负责什么。

## 5. 几个关键设计

### 5.1 规则匹配与连接去重

程序每次检查会再次看见仍然存在的连接。如果每次都写日志，一个持续一小时的连接会产生大量重复记录。`ConnectionTracker`因此保存当前观察状态：第一次看到时创建事件，继续看到时只更新时间，真正结束后才完成事件。

### 5.2 两秒结束宽限期

连接偶尔可能在一次读取中暂时缺失。程序不会立刻判定结束，而是按真实时间等待两秒。如果两秒内再次出现，仍算同一次观察；超过两秒才结束，结束时间使用最后一次真正看到它的时刻。

这个逻辑不能用“缺失两次”代替，因为检查间隔可以从0.5秒改到10秒。“两秒真实时间”在不同设置下含义保持一致。

### 5.3 动态检查间隔

用户可以在0.5到10秒之间调整间隔。监控循环不能只在启动时读取一次设置，否则修改后必须重启。

现在的设计在设置变化时发出信号，让正在等待的循环提前醒来，并使用新间隔继续。这里适合学习取消令牌、异步等待和并发状态保护。

### 5.4 清空界面不等于删除数据

“清空显示”只保存一个时间分界点，并隐藏更早的事件；CSV文件不变。这样既保持页面整洁，也保留调查资料。它体现了一个常见的软件设计原则：界面中的视图状态与底层数据生命周期应分开处理。

### 5.5 应用归属是证据，不是绝对结论

Windows连接表能提供进程ID，但“这个进程拥有连接”不一定等于“它是最终原因”。程序在新匹配出现时继续收集：

- Windows回报的连接拥有者和PID
- 可执行文件路径、产品名、公司和说明
- 最多三层父进程或宿主进程
- 与PID相关的Windows服务

这些信息能缩小调查范围，但浏览器、代理、VPN或内嵌网页组件可能早已在后台运行。因此界面和文档必须明确：它们是调查线索，不是自动定罪。

只在“新匹配”时收集这些资料，可以避免每0.5秒反复读取进程和文件信息。

### 5.6 CSV向后兼容

新版日志增加了程序背景字段，但用户可能已经有旧版12列或15列日志。读取器必须根据列数和表头识别旧格式，为缺失字段提供空值；写入器则使用当前20列格式。

修改持久化格式时，要同时考虑：新程序读旧数据、特殊字符转义、损坏行处理和测试样例。

### 5.7 手动更新检查的安全边界

只有用户点击“立即检查”时，程序才访问GitHub公开Release信息。它只告诉用户是否有新版并提供页面，不自动下载、运行或安装文件，也不上传规则或日志。

这能降低供应链和隐私风险，也让用户保持最终控制权。

## 6. 如何安全地修改一个功能

以“给事件增加一个字段”为例：

1. 先在`Models`中明确这个字段代表什么。
2. 在数据来源处收集它，不要让界面负责调查逻辑。
3. 更新`ConnectionEvent`和CSV读写。
4. 保证旧CSV仍能打开。
5. 在事件详情中显示；主表只保留最重要的摘要。
6. 为核心行为增加功能测试。
7. 检查七种语言和不同DPI下的布局。
8. 更新英文基准文档，再同步其余语言。
9. 在`RELEASE_NOTES.md`说明用户能感知的变化。

这条路线能避免“页面看起来改好了，但日志、兼容性或测试被遗漏”。

## 7. 构建、测试与发布

基础验证命令：

```powershell
dotnet build ConnectionWatcher.sln --configuration Release
dotnet run --project tests\ConnectionWatcher.Tests\ConnectionWatcher.Tests.csproj --configuration Release
```

维护者可以运行：

```powershell
scripts\build-release.ps1
```

脚本依次完成：

1. 构建解决方案。
2. 运行功能和兼容性测试。
3. 运行七种语言与多种DPI比例的界面测试。
4. 发布自包含的Windows程序到`artifacts`。
5. 用Inno Setup生成安装包到`dist`。
6. 把安装包、最新文档和发行说明整理到`Final-Share`。
7. 生成`SHA256SUMS.txt`。

`artifacts`是编译器的原始发布输出，`dist`是安装器的构建输出，`Final-Share`是给普通用户的最终分享内容。它们都可以重新生成，不应代替源代码。

## 8. 适合你的学习方法

建议每次只研究一个能在界面上观察到的小问题：

- 修改一个提示文字，理解本地化和布局。
- 给某个纯函数补一项测试，理解输入与输出。
- 跟踪一次规则匹配，画出函数调用路线。
- 用断点观察连接从“新建”到“结束”的状态变化。
- 对照CSV与事件详情，寻找每个字段的来源。
- 阅读一次Git提交的差异，理解一个功能横跨了哪些层。

不要以“能否一次读懂整个项目”衡量进度。更有效的标准是：今天能否解释清楚一个类、验证一个行为，并做一次小而安全的修改。

## 9. 可以继续深入的方向

当你能读懂当前项目后，可以继续学习：

- 用依赖注入替代部分手动创建对象。
- 把WinForms界面状态进一步与业务逻辑分离。
- 使用Windows事件追踪研究更强的网络归属能力。
- 为GitHub建立自动构建和Release流水线。
- 对配置与日志格式建立正式的版本迁移机制。

UDP并不是“再读一张表”这么简单。若要同时得到可靠的远程端点和应用归属，通常需要更底层、可能需要权限的事件追踪设计。因此当前版本保留TCP重点，是对软件核心目标和复杂度的主动取舍。
